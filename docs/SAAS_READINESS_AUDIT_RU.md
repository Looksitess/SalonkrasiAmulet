# Аудит готовности Salon SaaS

**Обновлено:** 2 ноября 2026 года  
**Репозиторий:** `Looksitess/SalonkrasiAmulet`  
**Production:** Supabase Postgres 17, один салон с slug `amulet`.

## Текущий итог

Проект стал tenant-aware для основных операций: публичная запись, список мастеров, услуги, отзывы и комментарии получают контекст через slug салона. Услуги и отзывы имеют `salon_id`; административная работа с ними ограничена текущим `salon_id` пользователя через RLS.

При этом продукт **ещё не готов к продаже как полностью работающий SaaS**: сейчас только один салон; публичный список мастеров пуст; реальную запись с клиентом и мастером не удалось проверить. Каталог Amulet уже заполнен 14 услугами и точными ценовыми подписями с текущей публичной страницы. Форум оставлен общей платформенной функцией.

## Изменения в Production и GitHub

### Онлайн-запись и мастера

- `create-booking` развёрнута как активная версия **14**. Проверяет JSON, slug салона, имя, телефон, услугу, UUID мастера, календарную дату, время и длину комментария; дополнительно ограничивает до 5 валидных заявок с одного номера на салон за 10 минут.
- Edge Function находит салон по проверенному slug, сверяет мастера с этим салоном, проверяет активность профиля и занятость через tenant-aware RPC.
- Сервер принимает только активную услугу из каталога салона. Для Amulet перенесены все 14 услуг, уже опубликованные на странице, с точными подписями цены, включая «від … грн».
- Запись получает `salon_id`, `master_id` и, когда услуга заведена в каталоге, `service_id`.
- `get_public_masters` и `get_public_available_times` теперь учитывают slug салона.
- `manage-masters` развёрнута как версия **7**. Исправлена ошибка удаления мастера без email/пароля; сервер проверяет формат запроса, UUID места, активность места и длину учётных данных. Привязка мастера выполняется условным UPDATE, который защищает от гонки двух одновременных запросов.
- Единственное включённое место №1 было связано с профилем администратора. Эта ошибочная связь отвязана. Профиль администратора сохранён, 133 строки графика сохранены, место освобождено для настоящего мастера.

### Дополнительная защита

- Старый прямой доступ к таблице `public_masters` закрыт для anon и authenticated; публичный каталог использует только `get_public_masters(salon_slug)`.
- Жалобы на отзывы и комментарии получили `salon_id` по связанному отзыву. Модерация таких жалоб ограничена салоном администратора; жалобы на общий форум остаются глобальными.
- `submit_customer_review` разрешена только роли authenticated. ACL-проверка подтвердила: anon — false, authenticated — true.
- Старый endpoint `admin-password-reset` отключён (410 Gone, JWT verification включён).
- Rate limiter хранит только HMAC-хеш номера + slug; исходный номер в таблице лимитов не сохраняется. RPC и таблица лимитов недоступны anon/authenticated.
- Транзакционный тест rate limiter подтвердил отказ после достижения лимита; транзакция откатилась и тестовая строка не сохранилась.

### Услуги и отзывы

- Добавлен `salon_id` с внешним ключом на `salons` в `services` и `customer_reviews`.
- Услуги, отзывы и комментарии больше нельзя напрямую читать анонимной ролью из таблиц. Публичный сайт использует узкие RPC-функции по slug: `get_public_services`, `get_public_approved_reviews`, `get_public_review_comments`, `get_public_masters`.
- Отправка отзыва выполняется через `submit_customer_review`, которая сама определяет `salon_id` по slug и берёт автора из `auth.uid()`; пользователь не может подставить чужой `salon_id`.
- RLS для модерации отзывов и комментариев ограничивает администратора своим салоном.
- Добавлена страница `admin/services.html` для добавления, редактирования и включения/отключения услуг. Она связана с админкой и позволяет сохранять точную подпись цены отдельно от числового значения.
- Публичный прайс и выпадающий список формы записи переключены на tenant-aware каталог. При ошибке или пустом каталоге статический прайс остаётся безопасным fallback.
- Длительность записи пока фиксирована в 60 минут, потому что текущая сетка времени и проверка занятости рассчитаны на часовые слоты. Панель услуг не позволяет задавать другую длительность, пока движок бронирования не будет расширен для пересечений разной длины.

### Админка и серверная безопасность

- Исправлена загрузка записей админки: результат запроса профилей теперь сохраняется корректно.
- Список записей отображается единым потоком, новые заявки — первыми; в карточке показывается время получения.
- Исправлены RLS-политики `master_slots`: все административные операции ограничены `private.current_salon_id()`.
- Старый endpoint восстановления пароля, который менял фиксированную учётную запись `admin@amulet.test` через общий секретный заголовок, отключён. Версия **3** возвращает `410 Gone` и требует JWT-проверку; старого изменения пароля больше нет.
- Добавлен GitHub Actions workflow с Deno lint, тестами валидации бронирования и проверкой синтаксиса основных страниц, включая страницу услуг.
- Добавлены `AGENTS.md`, `README_RU.md` и пять специализированных скиллов Codex.

## Проверки, выполненные после миграций

- Последняя проверка базы показала: 1 салон, 1 свободное включённое место мастера, 133 строки расписания, 0 заявок, 0 публичных мастеров, 14 услуг, 0 отзывов и 0 комментариев.
- Отвязка администратора от места мастера не удалила аккаунт или расписание.
- Имитация текущего администратора подтвердила, что RLS распознаёт его и определяет salon_id. Имитация пользователя без профиля администратора вернула отказ и 0 видимых строк в защищённых таблицах.
- Анонимной роли запрещён прямой SELECT на `services`, `customer_reviews` и `review_comments`; при этом разрешён только вызов публичных RPC-функций для отображения разрешённых данных.
- Выполнен transaction-only smoke test: временная услуга, отзыв и комментарий отображались через правильный slug, не отображались по чужому slug; затем транзакция откатилась. Проверка повторным подсчётом подтвердила, что временные строки не остались в базе.
- Исходники трёх Edge Functions в GitHub сверены с развёрнутыми версиями.
- Названия SQL-файлов миграций выровнены с версиями, записанными в истории Supabase.

## Что пока мешает коммерческому запуску

1. **Реального активного мастера пока нет.** Профиль администратора отвязан от места №1, но в Auth не создавался фиктивный мастер. После добавления реального мастера через админку список мастеров появится на сайте.
2. **Каталог услуг пока пуст.** Новая страница управления готова, но реальные названия, цены и длительности не добавлялись автоматически, чтобы не подменять фактический прайс салона.
3. **Реальная запись end-to-end не подтверждена.** Сервер и UI обновлены, но в базе нет мастера, который мог бы принять запись.
4. **Форум остаётся общим сообществом платформы.** Его модерация, реакции и жалобы пока не полностью разделены по салонам. Для SaaS нужно чётко оставить форум глобальным с отдельной ролью модератора платформы либо ввести tenant scope для всех этих сущностей.
5. **Не завершены процессы продукта:** автоматический onboarding салона, тарифы/оплата, обработка подписок, кастомные домены, экспорт/удаление данных, политика конфиденциальности, резервное копирование и поддержка.
6. **Ограничение частоты заявок реализовано по HMAC-хешу номера и slug салона: 5 валидных заявок за 10 минут. Полноценная антиспам-защита и ограничение по сетевому адресу ещё не реализованы.**
7. **Supabase Auth leaked-password protection остаётся выключенной.** В доступных инструментах нет операции изменения этой настройки; её нужно включить в настройках Supabase Auth до публичного запуска.
8. **GitHub Actions workflow добавлен, но результат его запуска здесь не подтверждён.** Нельзя считать CI зелёным до фактического успешного выполнения.

## Что требуется перед продажей

### P0 — подготовка Amulet к реальной работе
- Добавить реальный аккаунт мастера через админку и привязать его к свободному месту.
- Заполнить каталог фактическими услугами и ценами через страницу «Послуги».
- Проверить график, свободные часы, создание заявки, отказ при занятом времени, просмотр заявки администратором и мастером.
- Включить leaked-password protection и рассмотреть дополнительное ограничение по сетевому адресу.

### P1 — доказанная изоляция нескольких салонов
- Создать второй тестовый салон и отдельного администратора/мастера на синтетических данных.
- Проверить, что салон A не может читать/менять услуги, отзывы, комментарии, график, записи и места мастеров салона B.
- Разделить форумные возможности платформы и салонную модерацию жалоб/реакций.
- Проверить сценарии slug/domain для двух сайтов.

### P2 — SaaS-коммерциализация
- Автоматический onboarding салона, создание администратора и приглашение персонала.
- Настройки брендинга, контактов, часов работы и URL салона.
- Подписки, платежи, тарифные лимиты, отмена и просрочка.
- Экспорт и удаление данных, резервное копирование, журнал действий, поддержка и юридические документы.

## Важное ограничение

Сейчас нет активного публичного мастера и реальных строк в каталоге услуг. Поэтому, несмотря на внесённые изменения в код и RLS, сайт ещё нельзя честно рекламировать как полностью запущенную систему онлайн-записи и продавать как завершённый SaaS. Текущий результат — подготовленная tenant-aware основа и исправленная админка, которую нужно заполнить реальными данными и пройти сквозные проверки.
