# Аудит готовности Salon SaaS

**Обновлено:** 2 ноября 2026 года  
**Репозиторий:** `Looksitess/SalonkrasiAmulet`  
**Production:** Supabase Postgres 17, один салон с slug `amulet`.

## Текущий итог

Проект стал tenant-aware для основных операций: публичная запись, список мастеров, услуги, отзывы, комментарии, форум, жалобы и реакции получают контекст через slug/связь с салоном. Операционные и пользовательские записи разделены по `salon_id` напрямую или через родительскую запись; доступ браузера ограничен RLS и узкими RPC.

При этом продукт **ещё не готов к продаже как полностью работающий SaaS**: в базе пока один салон; публичный список мастеров пуст; реальную запись с действующим мастером пройти нельзя. Каталог Amulet заполнен 14 услугами и точными ценовыми подписями с публичной страницы. Форум, реакции и модерация теперь разделены по салонам.

## Изменения в Production и GitHub

### Онлайн-запись и мастера

- `create-booking` развёрнута как активная версия **16**. Проверяет JSON, slug салона, имя, телефон, услугу, UUID мастера, календарную дату, время и длину комментария; дополнительно ограничивает до 5 валидных заявок с одного номера на салон за 10 минут.
- Edge Function находит салон по проверенному slug, сверяет мастера с этим салоном, проверяет активность профиля и занятость через tenant-aware RPC.
- Сервер принимает только активную услугу из каталога салона. Для Amulet перенесены все 14 услуг, уже опубликованные на странице, с точными подписями цены, включая «від … грн».
- Запись получает `salon_id`, `master_id` и, когда услуга заведена в каталоге, `service_id`.
- `get_public_masters` и `get_public_available_times` теперь учитывают slug салона.
- `manage-masters` развёрнута как версия **9**. Исправлена ошибка удаления мастера без email/пароля; сервер проверяет формат запроса, UUID места, активность места и длину учётных данных. Привязка мастера выполняется условным UPDATE, который защищает от гонки двух одновременных запросов.
- Единственное включённое место №1 было связано с профилем администратора. Эта ошибочная связь отвязана. Профиль администратора сохранён, 133 строки графика сохранены, место освобождено для настоящего мастера.

### Дополнительная защита

- Старый прямой доступ к таблице `public_masters` закрыт для anon и authenticated; публичный каталог использует только `get_public_masters(salon_slug)`.
- Жалобы на отзывы, комментарии, темы и ответы получают `salon_id` по целевому объекту. Администратор видит и модерирует только жалобы своего салона.
- `submit_customer_review` разрешена только роли authenticated. ACL-проверка подтвердила: anon — false, authenticated — true.
- Старый endpoint `admin-password-reset` отключён (410 Gone, JWT verification включён).
- Rate limiter хранит только HMAC-хеш номера + slug; исходный номер в таблице лимитов не сохраняется. RPC и таблица лимитов недоступны anon/authenticated.
- Транзакционный тест rate limiter подтвердил отказ после достижения лимита; транзакция откатилась и тестовая строка не сохранилась.

### Услуги и отзывы

- Добавлен `salon_id` с внешним ключом на `salons` в `services` и `customer_reviews`.
- Услуги, отзывы и комментарии больше нельзя напрямую читать анонимной ролью из таблиц. Публичный сайт использует узкие RPC-функции по slug: `get_public_services`, `get_public_approved_reviews`, `get_public_review_comments`, `get_public_masters`.
- Отправка отзыва выполняется через `submit_customer_review`, которая сама определяет `salon_id` по slug и берёт автора из `auth.uid()`; пользователь не может подставить чужой `salon_id`.
- RLS для модерации отзывов и комментариев ограничивает администратора своим салоном.
- Добавлена страница `admin/services.html` для добавления, редактирования и включения/отключения услуг. Она связана с админкой и позволяет сохранять точную подпись цены отдельно от числового значения.
- Публичный прайс и выпадающий список формы записи переключены на tenant-aware каталог. При ошибке или пустом каталоге публичный прайс остаётся fallback, но выбор услуги блокируется с понятным сообщением, а сервер отклоняет запись без активной услуги.
- Поле длительности пока остаётся 60 минут по техническому ограничению текущей сетки слотов; это не подтверждённая фактическая длительность каждой процедуры. До перехода на интервальное бронирование нужно уточнить реальные длительности и реализовать проверку перекрытий.

### Админка и серверная безопасность

- Исправлена загрузка записей админки: результат запроса профилей теперь сохраняется корректно.
- Список записей отображается единым потоком, новые заявки — первыми; в карточке показывается время получения.
- Исправлены RLS-политики `master_slots`: все административные операции ограничены `private.current_salon_id()`.
- Старый endpoint восстановления пароля, который менял фиксированную учётную запись `admin@amulet.test` через общий секретный заголовок, отключён. Версия **3** возвращает `410 Gone` и требует JWT-проверку; старого изменения пароля больше нет.
- Форум стал отдельным для каждого салона: у тем есть обязательный `salon_id`; ответы наследуют его через тему. Публичное чтение идёт через `get_public_forum_topics(slug)` и `get_public_forum_posts(slug, topic_id)`; создание — через RPC, которые требуют authenticated-сеанс. Прямые анонимные чтение и вставка в forum tables закрыты.
- Модерация форума ограничена салоном администратора. Жалобы на форум/отзывы также автоматически получают салон целевого объекта.
- Реакции/лайки получили `salon_id`. Прямые SELECT/INSERT/DELETE к таблице закрыты браузерным ролям; чтение отдаёт только количество и признак лайка текущего пользователя через `get_public_content_reactions`, переключение выполняется атомарно через `toggle_public_content_reaction`.
- Добавлен GitHub Actions workflow с Deno lint, тестами валидации бронирования и проверкой синтаксиса основных страниц, включая страницу услуг.
- Добавлены `AGENTS.md`, `README_RU.md` и пять специализированных скиллов Codex.

## Проверки, выполненные после миграций

- Последняя проверка базы показала: 1 салон, 1 включённое свободное место мастера без профиля, 133 строки расписания, 0 заявок, 0 публичных мастеров, 14 услуг, 0 отзывов, 0 комментариев, 0 тем/ответов форума, 0 жалоб и 0 реакций.
- Отвязка администратора от места мастера не удалила аккаунт или расписание.
- Имитация текущего администратора подтвердила, что RLS распознаёт его и определяет salon_id. Имитация пользователя без профиля администратора вернула отказ и 0 видимых строк в защищённых таблицах.
- Анонимной роли запрещён прямой SELECT на `services`, `customer_reviews` и `review_comments`; при этом разрешён только вызов публичных RPC-функций для отображения разрешённых данных.
- Выполнен transaction-only smoke test: временная услуга, отзыв и комментарий отображались через правильный slug, не отображались по чужому slug; затем транзакция откатилась. Проверка повторным подсчётом подтвердила, что временные строки не остались в базе.
- Форум проверен на двух временных салонах в rollback-транзакции: публичные RPC возвращают записи по нужному slug; RLS-сеанс администратора Amulet видит только тестовую тему и ответ собственного салона, но не второго. Все синтетические строки откатились.
- Реакции проверены в rollback-транзакции: toggle включал/выключал лайк, счётчик и флаг текущего пользователя обновлялись, запросы по чужому slug не возвращали чужие реакции. Тестовые салон, темы и реакции откатились.
- После ограничения реакций прямые права браузерных ролей на таблицу сняты: anon/authenticated не имеют SELECT/INSERT/DELETE, а toggle-RPC недоступен anon.
- JavaScript синтаксис проверен после последних изменений: 20 inline/external скриптов на семи страницах и файлах разобраны без ошибок.
- Исходники трёх Edge Functions в GitHub сверены с развёрнутыми версиями.
- Названия SQL-файлов миграций выровнены с версиями, записанными в истории Supabase.
- Уникальность `master_slots.slot_number` теперь составная по `(salon_id, slot_number)`, поэтому каждый салон может иметь собственную нумерацию мест 1–20.
- Временный второй салон проверен в транзакции: RPC возвращали его услуги/отзыв только по его slug, а администратор Amulet не видел данные второго салона в услугах, отзывах, местах мастеров, записях, графике и закрытых часах.
- Rate-limit проверен полным циклом: первые 5 запросов разрешены, шестой блокируется; транзакция откатилась.
- Временный второй салон был создан внутри одной транзакции: его услуги/отзывы возвращались только по его slug, а администратор Amulet не видел его услуги, отзывы, места мастеров, записи, график и закрытые интервалы. Вся QA-транзакция откатилась.
- `bookings.salon_id` теперь `NOT NULL` с FK на `salons`; составные FK `(master_id, salon_id)` и `(service_id, salon_id)` не позволяют создать запись с мастером/услугой другого салона. Транзакционный тест подтвердил отказ для чужого мастера, чужой услуги и NULL salon_id; удаление тестовых ссылок очищало только master_id/service_id, сохраняя booking и salon_id. QA-транзакция откатилась.

## Важный долг по воспроизводимости базы

- В production отмечена 31 применённая миграция; в GitHub сохранены 22 исходных SQL-файла.
- Отсутствуют оригинальные файлы десяти исторических миграций; их точные версии перечислены в `supabase/migrations/README_RU.md`.
- Поэтому текущая production-база работает, но развернуть идентичную базу с нуля только из репозитория пока нельзя. Не запускать `supabase db reset` и не создавать фиктивные миграции-заглушки.
- До коммерческого тиражирования нужно восстановить оригинальные SQL или подготовить и проверить полный bootstrap snapshot на отдельной пустой базе.

## Что пока мешает коммерческому запуску

1. **Реального активного мастера пока нет.** Профиль администратора отвязан от места №1, но в Auth не создавался фиктивный мастер. После добавления реального мастера через админку список мастеров появится на сайте.
2. **Каталог услуг заполнен 14 позициями.** Названия и ценовые подписи перенесены из текущей публичной страницы Amulet; на странице администратора можно обновлять их. Длительности пока фиксированы в 60 минут из-за ограничений текущего планировщика.
3. **Реальная запись end-to-end не подтверждена.** Сервер и UI обновлены, но в базе нет мастера, который мог бы принять запись.
4. **Полная проверка с двумя отдельными Auth-аккаунтами ещё не выполнена.** Tenant-изоляция услуг, отзывов, расписаний, записей, форума, жалоб и реакций уже проверялась транзакционными сценариями; для финальной приёмки нужны отдельный администратор и реальный мастер второго салона.
5. **Не завершены процессы продукта:** автоматический onboarding салона, тарифы/оплата, обработка подписок, кастомные домены, экспорт/удаление данных, политика конфиденциальности, резервное копирование и поддержка.
6. **Ограничение частоты заявок реализовано по HMAC-хешу номера и slug салона: 5 валидных заявок за 10 минут. Полноценная антиспам-защита и ограничение по сетевому адресу ещё не реализованы.**
7. **Supabase Auth leaked-password protection остаётся выключенной.** В доступных инструментах нет операции изменения этой настройки; её нужно включить в настройках Supabase Auth до публичного запуска.
8. **GitHub Actions workflow добавлен, но результат его запуска здесь не подтверждён.** Нельзя считать CI зелёным до фактического успешного выполнения.

## Важное ограничение

Сейчас нет активного публичного мастера; каталог из 14 услуг уже заполнен. Поэтому, несмотря на внесённые изменения в код и RLS, сайт ещё нельзя честно рекламировать как полностью запущенную систему онлайн-записи и продавать как завершённый SaaS. Текущий результат — подготовленная tenant-aware основа и исправленная админка, которую нужно заполнить реальными данными и пройти сквозные проверки.


## Android administration build

- The native Android admin shell is a WebView over the published `/admin/` site and uses the same current Supabase-backed admin interface.
- The Play release workflow now skips signing when its four protected upload-key secrets are absent; it does not generate a new key in a public repository.
- When the secrets exist, only APK/AAB are uploaded as an artifact. The keystore and its passwords are not included in the downloadable package.
- The workflow itself has not been run/verified in this audit; the Android release build is not yet confirmed.
