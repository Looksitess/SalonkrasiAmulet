# Аудит готовности Salon SaaS

**Снимок состояния:** 1 ноября 2026 года  
**Репозиторий:** `Looksitess/SalonkrasiAmulet`  
**Текущая база:** один салон Amulet, Supabase Postgres 17.

## Итог

Текущий проект — работающий по своей архитектуре односалонный веб-сайт с онлайн-записью, админ-панелью, несколькими мастерами, отзывами и форумом. Он **пока не подтверждён как коммерчески готовая многосалонная SaaS-платформа**.

## Уже подтверждено в исходниках и базе

- Есть публичная форма записи и серверная Edge Function `create-booking`.
- Есть проверка свободного времени через `get_public_available_times`.
- В БД есть уникальный частичный индекс на активный слот записи по салону, мастеру, дате и времени — защита от двух активных записей в один слот на уровне БД.
- Есть таблицы салонов, профилей, мест мастеров, графиков и закрытых интервалов.
- Профили и бронирования уже содержат `salon_id`.
- В базе на момент аудита один салон, 20 мест мастеров и один администраторский профиль.
- Исходники Edge Functions `manage-masters` и `admin-password-reset` синхронизированы с тем, что развёрнуто в Supabase.
- Добавлены проектные инструкции Codex в `AGENTS.md` и пять скиллов в `.agents/skills/`.
- Публичная Edge Function записи усилена строгой серверной проверкой полей, UUID, календарной даты, времени по Europe/Kyiv и размера тела запроса. Версия 9 развёрнута.

## Подтверждённые ограничения для SaaS

1. **Публичная запись всё ещё привязана к Amulet.** `create-booking` выбирает салон по slug `amulet`; RPC свободных времён тоже ограничивает выбор этим slug.
2. **Услуги не имеют `salon_id`.** Текущая публичная политика читает все активные услуги; полноценной изоляции услуг между салонами пока нет.
3. **Отзывы не имеют `salon_id`.** Публичные отзывы и административные policies сейчас глобальные. Для отдельных сайтов салонов это может привести к пересечению отзывов и прав модерации.
4. **Нумерация мест мастеров глобально уникальна.** Уникальность `slot_number` пока не составная по `salon_id`, поэтому независимые салоны не могут безопасно вести собственную нумерацию мест мастеров.
5. **Форум и его модерация глобальные.** Это допустимо только как осознанное общее сообщество платформы; если форум должен быть отдельным у каждого салона, потребуется tenant scope для тем, ответов, реакций и жалоб.
6. **Нет доказанного теста двух арендаторов.** Нельзя утверждать, что администратор салона A не увидит данные салона B, пока не создан второй тестовый салон и не пройдены негативные проверки.
7. **Проверка паролей на утечки отключена** в Supabase Auth по результатам Security Advisor. Это требуется включить до публичного коммерческого запуска.
8. **Функция восстановления пароля использует общий секретный заголовок и фиксированную учётную запись `admin@amulet.test`.** Её нужно заменить стандартным безопасным восстановлением Supabase Auth или удалить после подтверждения, что она больше не используется; нельзя публиковать или повторно использовать reset token.
9. **Не подтверждены** rate limiting публичных заявок, антиспам на сервере, сквозные тесты реальной записи и тесты восстановления после сбоя.
10. **Не подтверждены коммерческие процессы:** онбординг салона без ручного SQL, тарифы/подписки и платежи, кастомные домены/slug, экспорт и удаление данных клиента, политика конфиденциальности, резервное копирование и процесс поддержки.

## План до коммерческого запуска

### P0 — безопасность и сохранение текущей работы
- Пройти сквозной happy-path тест записи и отказ при занятом слоте.
- Прогнать GitHub Actions.
- Проверить вход администратора и мастера, загрузку списка записей и расписания.
- Пересмотреть recovery endpoint и включить leaked-password protection.

### P1 — настоящий multi-tenant
- Ввести tenant-aware публичное разрешение салона по проверенному slug/domain.
- Добавить `salon_id` в услуги и отзывы; определить tenant scope для комментариев, реакций и жалоб.
- Обновить policies, RPC, Edge Functions и frontend на один и тот же tenant resolver.
- Сделать `slot_number` уникальным в пределах салона, а не всей платформы.
- Явно решить: форум глобальный или отдельный для салона. Не смешивать оба режима.
- Создать два синтетических салона и протестировать перекрёстный отказ чтения/записи для anon, admin и master.

### P2 — коммерческий продукт
- Автоматический онбординг, branding settings, страницы и URL для новых салонов.
- Ролевой доступ и приглашения сотрудников с аудит-журналом.
- Управление услугами и ценами из админки.
- Серверная антиспам-защита и безопасные ограничения частоты.
- Подписки/платежи, тарифные ограничения, отмена и просрочка.
- Резервное копирование, экспорт/удаление данных, документы приватности и поддержка.

## Ограничения проверки

- Автоматические тесты добавлены, но до завершения GitHub Actions не отмечены как пройденные.
- Сквозная запись в живой production базе в этом этапе не выполнялась, чтобы не создавать фиктивные записи клиентов.
- Не выполнялись разрушительные DDL изменения и не менялись RLS политики, у которых есть связанные роли/функции.
- Развёртывание версии 9 подтверждено ответом Supabase; это не заменяет тест реального UI с авторизованным администратором.
